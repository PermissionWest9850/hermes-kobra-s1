This is a **local, unreleased implementation of steps 1–5**. It is not a
completed v0.3.0 release. The current installation/toolchain has successfully
completed a fresh **Minimal-Debian-13** validation without `sudo`, using exactly
one native `su` root authentication. Printer access was limited to read-only
status checks; no physical routing, movement, heating, upload or print was tested.
Hermes authentication remains **pending** and exact ACE model identity remains
**NOT VERIFIED**. Debian 12 and Ubuntu 24.04 remain untested; no additional
distribution support is claimed.

Steps 1–2 remain the accepted baseline. Steps 3–4 introduce only a separate
KlipperMCP setup helper (fresh lockfile installation vs read-only reuse) and the
shared read-only Doctor. See [dependency details](klippermcp-dependencies.md)
and [Doctor contract](doctor.md). Step 5 adds the separate, local-only
[`--update-profiles` mechanism](update-profiles.md): field comparison, explicit
TTY confirmation, verified private backup, conflict detection and failure rollback.
Existing profile files and convenience launchers are not migrated silently.

## Existing Hermes profile files

The normal installer creates the initial managed payload, but a rerun preserves
all existing managed files, including local edits and extra files under the
managed directories:

- `config.yaml`
- `SOUL.md`
- `scripts/`
- `patches/`
- `distribution.yaml`
- `.env.EXAMPLE`
- `checksums/` (introduced in this preparation)

An incomplete or type-inconsistent old payload is refused without partial
regeneration. A complete v0.2.0 payload without `checksums/` is a recognized
migration case: a normal rerun still does not add or replace anything.
Symlinks and special files in managed payloads are refused. `.env` is not read,
backed up or replaced by the configuration helper.

### Explicit local update

From the complete local clone:

```bash
bash install.sh --update-config --dry-run
bash install.sh --update-config
```

`PROFILE_DIR` can select a target; otherwise the existing installer profile-home
resolution is used. Review that target before confirming. This mode runs before
normal installation: no sudo/su authentication, APT, download, Hermes onboarding,
KlipperMCP build, Moonraker request, Orca-profile generation or printer action.
Python 3 must already be present; the mode does not install it.

The preview lists ADD/CHANGE/REMOVE paths, including user-added files that would
be removed by replacing the managed directories. It intentionally does not show
configuration contents: `config.yaml`, scripts and other files can contain
private values. This is a comparison summary, **not a content diff or YAML
schema validator**. Configuration changes are not auto-merged.

Replacement requires the exact phrase `UPDATE CONFIG` on an interactive TTY.
`--yes`, an environment variable or piped input cannot approve it. A dry run
never asks for approval or creates a backup/staging area.

After approval:

1. Check again that the original payload has not changed.
2. Acquire a nonblocking profile-update lock and stage the candidates locally.
   Compare the source and staged candidates to the **source fingerprint used
   for the preview**, not a new post-confirmation baseline. Changed candidates
   are refused before creating a backup or moving any target root.
3. Copy the original managed payload to a restricted backup directory:
   `PROFILE_DIR/backups/config-TIMESTAMP-UNIQUEID/`.
4. Verify contents/types/modes against the original fingerprint. Store original
   and candidate fingerprints in `backup-manifest.json`; no file contents or
   `.env` values are in that manifest.
5. Recheck the target, move **all** original managed roots into local staging,
   then compare those actual moved originals to the approved fingerprint before
   publishing any candidate. Edits detected during those moves cancel the update
   and the moved revisions are restored, rather than replaced with backup copies.
6. Publish roots using Linux atomic no-overwrite rename (`renameat2` with
   `RENAME_NOREPLACE`). A new root appearing during the transaction is not
   overwritten, including an empty directory or symlink. Unsupported filesystem
   behavior fails closed; there is no check-then-overwrite fallback.
7. On success, retain the actual original inodes under the restricted backup's
   `moved-originals/`, in addition to the verified pre-update copy. An editor
   holding an old descriptor can still write there later; these retained inodes
   are **not** an immutable snapshot and may differ from `backup-manifest.json`.
8. On failure, withdraw this transaction's published roots into recovery
   staging without deleting their possibly edited contents. Restore moved
   originals only into absent paths. A conflicting new root stays in place and
   its displaced original stays in `originals/` for manual recovery. Staging is
   retained on every failed transaction, even after a successful rollback.

Multiple roots are **not a single atomic transaction**. SIGKILL, power loss or a
persistent filesystem fault can leave an incomplete payload. Retained
`.config-stage-*` and verified backups must not be deleted blindly; inspect and
restore explicitly before retrying. The helper does not guarantee protection
against an actively malicious process running with the same user permissions.
The profile lock serializes this helper, not arbitrary editors. Close editors
before updating. Late descriptor edits are preserved for recovery, not merged
into the newly installed configuration. Inspect `originals/`, `withdrawn/`,
backup copies and `moved-originals/` before manually choosing a revision.

Backups may contain private values in user-edited configuration/scripts; keep
them local. Their root directories use mode 0700 and the fingerprint manifest
uses mode 0600. Do not publish a backup in a bug report.

## OrcaSlicer 2.4.2 x86_64 trust decision

Manifest: [`../checksums/orcaslicer-2.4.2.json`](../checksums/orcaslicer-2.4.2.json).

The review used two separately published digests for the exact same file:

- GitHub release API SHA256 for
  `OrcaSlicer_Linux_AppImage_Ubuntu2404_V2.4.2.AppImage`.
- AUR Community `orca-slicer-bin 2.4.2-1` SHA512, pinned to historical commit
  `e1534f0c9d510c075e67c30e297e6efe3c4cfa15`.

Both digests were independently computed against the already existing local
AppImage and matched those published values before the manifest was created.
This is a separately published **community trust anchor**, not an official Arch
package, authenticated upstream signature or build attestation. An AUR
maintainer may have obtained the file from the same upstream download. The
additional publication does not prove independent build reproduction or that
the binary is harmless.

Sources:

- <https://api.github.com/repos/OrcaSlicer/OrcaSlicer/releases/tags/v2.4.2>
- <https://aur.archlinux.org/cgit/aur.git/plain/PKGBUILD?h=orca-slicer-bin&id=e1534f0c9d510c075e67c30e297e6efe3c4cfa15>

### Installer rules

- Resolve exactly one official asset, then require its exact pinned filename.
- Accept only the expected official GitHub release URL (including the upstream
  repository rename).
- Require **both** the reviewed SHA256 and AUR SHA512. Missing/malformed manifest,
  wrong version/architecture/asset or a digest mismatch stops installation.
  The schema version must be integer `1` (not boolean/float); duplicate JSON
  keys are rejected at every object level.
- Never take a new expected digest from live download metadata at runtime.
- Open the downloaded artifact with `O_NOFOLLOW`, require a regular descriptor,
  and compare descriptor/path device and inode identities before and after
  hashing, with size/mtime/ctime checks during hashing.
- Keep that descriptor open through chmod and extraction, executing
  `/proc/self/fd/N` with the descriptor inherited by the child, never reopening
  the download pathname to execute it. Extraction runs in a private temporary
  staging directory before publication.
- Rehash the held artifact after extraction, copy from that same descriptor to
  an exclusively created destination, and verify the destination's actual bytes
  and identity before making it executable. Existing destinations are never
  overwritten. A publication/extraction-tree failure can leave an incomplete
  fresh installation; resolve it explicitly rather than retrying as a repair.
- Check existing complete user-local or `/opt` installations by hashing only;
  reuse matching AppImages without execution or changing extracted profiles.
- Refuse unknown/mismatching or incomplete existing installations. No automatic
  replacement or repair, no optional TLS-only fallback and no bypass flag.

The AppImage digest does **not** validate a separately modified existing
`squashfs-root` tree. Those profiles remain unchanged on rerun and are not
presented as independently checksum-verified. The security of the reviewed
manifest still depends on the trusted checkout/installer; this is not a signed
project release or protection against compromise of this repository.
Descriptor binding prevents pathname substitution, not actively malicious
same-UID writes to the already-open inode or its extracted tree. The private
temporary directory and trusted checkout remain part of the boundary.

A separate local integration check subsequently ran the descriptor-bound
extraction/publication path against a **copied real x86_64 OrcaSlicer 2.4.2
AppImage**, inside an ignored clone-local temporary directory. Extraction,
published-file SHA256/SHA512 verification and the three expected Kobra S1
profile files passed. Generated test outputs were removed; the original `/opt`
installation was neither executed nor modified. This is a host-local test, not
a fresh-VM installation, headless-slicing test or printer-hardware test.

### aarch64

The manifest records the observed same-source GitHub digest for transparency,
but deliberately does not approve automatic verification. Without a comparable
reviewed additional anchor, automatic installation **and reuse** through this
installer are blocked. No equivalent security claim is made. Adding a trusted
architecture requires a separate provenance review, not an environment override.

## Local validation

```bash
python3 -B -m unittest discover -s tests -v
bash -n install.sh
git diff --check
```

Tests exercise profile preservation, explicit update, backup validation,
rollback/recovery, migration, secret-free preview and checksum failures. Download
integration tests use clearly synthetic local artifacts and a curl fixture:
these are not real GitHub downloads, real Orca executions or Clean-VM tests.
One optional test hashes a pre-existing official AppImage read-only when present;
it does not download, execute, replace or extract that installation.

Clean-VM tests, real hardware tests, commits and pushes require separate approval.
Upload and print start remain two separate explicit approvals; neither is used
in this validation.
